# Размеры карточек (size) и теги

Дата обнаружения: 2026-08-21. Источник: живая работа с пространством 18191
(kaiten.x5.ru) — при создании девяти карточек `size` не проставился ни через
`kaiten_create_card`, ни через `kaiten_update_card`, а теги пришлось навешивать
напрямую через REST.

---

## 1. BUG: `size` молча игнорируется при create/update — исправлено

### Симптом

`kaiten_create_card` и `kaiten_update_card` принимали `size: number`, возвращали
успешный ответ, но у карточки оставались `size: null`, `size_unit: null`,
`size_text: null`. Ошибки не было — операция выглядела успешной.

### Корневая причина

Kaiten не принимает `size` и `size_unit` в теле `POST /cards` и
`PATCH /cards/{id}` — это вычисляемые поля только на чтение. Единственное
записываемое поле — `size_text` (строка), из которой сервер сам выводит пару
`size` + `size_unit`. Документация API перечисляет допустимые значения:
`'1'`, `'23.45'`, `'.5'`, `'S'`, `'3 M'`, `'L'`, `'XL'`.

Проверено прямыми REST-запросами (карточка со стартовым `2 SP`):

| Тело запроса                     | Результат          |
| -------------------------------- | ------------------ |
| `{"size": 3}`                    | без изменений, 200 |
| `{"size": 3, "size_unit": "SP"}` | без изменений, 200 |
| `{"size_text": "2 SP"}`          | применяется        |

Второй слой проблемы: даже корректный `size_text` применяется не везде. В Kaiten
`size` — настраиваемое свойство карточки, привязанное к доске и типу
(`board.card_properties[] = {key: "size", cardTypeIds: [...], required: bool}`).
Там, где свойство для типа не включено, сервер снова отвечает 200 и тихо
отбрасывает значение.

### Что сделано

- Трансляция `size` → `size_text` внутри инструментов (v3.4.0, коммит `272cb89`):
  в тело запроса уходит только `size_text`, ключи `size` / `size_unit` не
  пробрасываются.
- Опциональный параметр `size_unit` у `kaiten_create_card` и
  `kaiten_update_card`: `size: 3` + `size_unit: "SP"` → `size_text: "3 SP"`.
  Без единицы уходит голое число — API это допускает.
- `assertSizeApplied` ([src/tools/helpers.ts](../src/tools/helpers.ts)): после
  записи сверяем `card.size` с запрошенным значением. При расхождении инструмент
  возвращает `VALIDATION_ERROR` вместо «успеха». В сообщении — id карточки,
  отправленный `size_text` и фактическое значение; в `hint` — причина: если
  свойство `size` не покрывает `type_id` карточки, текст называет доску и тип.
- Отдельно оговорено, что карточка при `kaiten_create_card` **уже создана**:
  hint велит чинить оценку через `kaiten_update_card`, а не повторять создание.

Тихий no-op со стороны Kaiten больше не выглядит как применённое изменение.

## 2. FEATURE: инструменты для тегов — исправлено

### Что сделано

- `kaiten_add_card_tags` — навесить теги по именам (Kaiten создаёт тег, если
  такого имени ещё нет).
- `kaiten_remove_card_tags` — снять теги по именам; имена резолвятся в id через
  `GET /cards/{id}/tags`.

Оба пакетные, по схеме continue-on-error (см. CONTRIBUTING, «Пакетные операции
со связями»).

- `kaiten_list_tags` — поиск тега компании по подстроке (`GET /tags?query=`),
  возвращает `id` + `name`. Закрывает тупик: `kaiten_search_cards` умел
  фильтровать по `tag_ids`, но узнать сам `tag_id` было нечем. Параметр поиска
  сделан **обязательным** на уровне схемы, а не опциональным с дефолтом:
  `GET /tags` без `query` отдаёт только первые 100 тегов и игнорирует `limit`,
  то есть вызов без подстроки выглядел бы успешным, молча не найдя нужный тег.
  Это тот же класс ошибки, что и пункт 1.
